# 천지인 키보드 & IME — 기획서

> 프로젝트 코드명: **Cheonjiin Unified IME (CU-IME)**
> 대상 플랫폼: Windows · macOS · Linux · Android · iOS
> 문서 버전: 1.0 / 2026-08-17

---

## 1. 배경

천지인은 2011년 방송통신위원회가 3×4(12키) 전화기용 한글 자판의 **국가 산업 표준**으로 채택한 배열이다. 당시 방통위 결정에 따라 배열 특허가 개방되어, 국내외 어느 기기에서나 자유롭게 구현할 수 있다. ([방통위 표준 예고고시 자료](http://www.simplecode.net/xe/18731), [자판 역사 정리](https://pat.im/1027))

천지인은 하늘(ㆍ)·땅(ㅡ)·사람(ㅣ) 삼재(三才)를 조합해 21개 모음 전체를 3개 키로 생성하는 구조로, 훈민정음 제자 원리를 그대로 입력 규칙에 옮긴 배열이다. ([원천 특허 KR20000049347A](https://patents.google.com/patent/KR20000049347A/ko))

### 문제 정의

천지인은 **모바일에만 갇혀 있다.** 현재 상황:

| 플랫폼 | 천지인 지원 현황 |
|---|---|
| Android | 삼성 키보드 등 기본 제공 (사실상 표준) |
| iOS | 서드파티 앱만 존재, 품질 편차 큼 |
| Windows | **사실상 없음** (MS IME 미지원) |
| macOS | **사실상 없음** |
| Linux | **사실상 없음** |

이로 인해 발생하는 실질적 손실:

1. **근육 기억의 단절** — 모바일에서 천지인에 완전히 숙달된 사용자가 PC에서는 두벌식을 별도로 익혀야 한다.
2. **접근성 공백** — 천지인은 키 수가 적어(12키) 운동 장애·저시력 사용자에게 두벌식(33키)보다 유리하지만, PC 보조기기 환경에서 선택지가 없다.
3. **구현 파편화** — 각 앱이 조합 규칙을 제각기 해석해 `ㅘ`, 겹받침, 백스페이스 동작이 서로 다르다. 삼성 '천지인 플러스'조차 쌍자음 입력에서 `했다`→`해ㅆ다` 같은 조합 버그가 사용자 신고로 이어졌다. ([사용자 리포트](https://www.clien.net/service/board/cm_iphonien/7257175))

### 기회

문제 3(파편화)이 곧 해법의 열쇠다. **조합 엔진을 플랫폼 독립적인 순수 상태 머신으로 한 번만 정확히 구현하면**, 5개 플랫폼은 각자의 IME 프레임워크에 이 코어를 연결하는 얇은 셸(shell)만 만들면 된다. 조합 규칙은 플랫폼과 무관한 순수 함수이므로, 코어의 정확성이 곧 전 플랫폼의 정확성이 된다.

## 2. 목표

### 제품 목표

| # | 목표 | 성공 지표 |
|---|---|---|
| G1 | 5개 플랫폼에서 **동일한 키 시퀀스 → 동일한 결과** | 공용 테스트 벡터 100% 일치 |
| G2 | 조합 정확성 | 현대 한글 11,172자 왕복 무결성 100% |
| G3 | 학습 비용 최소화 | 모바일 숙련자가 PC에서 재학습 없이 사용 |
| G4 | 접근성 | WCAG 2.2 AA, 스위치/스캐닝 입력 지원 |

### 비목표 (Non-goals)

명시적으로 **하지 않는 것**:

- 옛한글(ㆍ, ㅿ, ㆆ 등) 입력 — v2 이후 검토
- 예측 입력/자동완성 엔진 자체 개발 — OS 제공 API 활용에 그침
- 나랏글·SKY 등 타 12키 배열 지원 — 아키텍처상 확장 가능하게 두되 v1 범위 외
- 필기/음성 입력
- **천지인으로 두벌식보다 빠른 입력** — 후술하듯 물리적으로 불가능하며, 목표로 삼지 않는다

## 3. 핵심 설계 판단: 천지인은 느리다, 그것을 인정하고 시작한다

기획 단계에서 가장 중요한 정직한 인식이다. 참조 엔진으로 실측한 결과:

| 지표 | 실측값 |
|---|---|
| 현대 한글 11,172자 평균 타수 | **7.03타/자** |
| 실전 문장 기준 두벌식 대비 | **1.53배** (296타 vs 194타) |
| 중성 21자 평균 | 2.95타 |
| 초성 19자 평균 | 1.89타 |

> 측정 방법: `tools/verify.py`. 두벌식은 자모 1타 + 쌍자음/ㅒㅖ Shift 1타 + 복합모음 분해 타수로 계산.

**즉 천지인은 두벌식보다 약 1.5배 많은 타수를 요구한다.** 이는 12키에 33자모를 눌러 담은 구조상 필연적이며, 어떤 최적화로도 뒤집을 수 없다.

따라서 이 프로젝트의 가치 제안은 "빠른 입력"이 아니라 다음 세 가지다:

1. **연속성** — 이미 천지인에 숙달된 손을 PC에서도 그대로 쓴다.
2. **좁은 공간** — 12키는 물리 공간·시선 이동·오타율에서 유리하다.
3. **접근성** — 키 개수가 적다는 것은 곧 도달 가능한 타깃이 크다는 뜻이다.

이 인식은 스펙에도 반영된다. 타수를 줄이는 것이 목표가 아니므로, **모호성 제거와 예측 가능성**을 타수보다 우선한다(§4의 설계 원칙 P2).

## 4. 설계 원칙

**P1. 코어는 순수하다.**
조합 엔진은 `(상태, 키) → (상태, 출력)`의 순수 함수다. I/O·타이머·플랫폼 API를 일절 포함하지 않는다. 멀티탭 타임아웃조차 코어 밖에서 `TIMEOUT` 키로 주입한다. 이래야 5개 플랫폼이 같은 테스트 벡터를 공유할 수 있다.

**P2. 모호하면 타수를 늘린다.**
멀티탭 방식의 고질적 문제는 `ㄱㄱ`(각각) 같은 연속 동일 키다. 이를 타임아웃으로만 해결하면 사용자가 "기다려야 하는" 불확실성이 생긴다. 우리는 획추가(`*`)·쌍자음(`#`) 키로 **결정적 대체 경로**를 항상 제공한다. 1타 더 들더라도 기다림이 없는 쪽을 택한다.

**P3. 되돌릴 수 있어야 한다.**
백스페이스는 글자가 아닌 **자모 단위 역추적**이다. `나`에서 백스페이스 시 `ㄴ`이 아니라 `니`가 되어야 한다(마지막 입력 `ㆍ`만 취소). 이는 조합 상태의 역방향 전이로 구현하며, 실측 검증 대상이다.

**P4. 플랫폼 관례를 이긴다고 착각하지 않는다.**
각 OS의 IME 규약(preedit/marked text, 커밋 타이밍)을 존중한다. 특히 iOS는 조합 중 텍스트(marked text) API가 제한적이므로, 그 제약을 우회하지 않고 설계에 반영한다(스펙 §7 참조).

## 5. 사용자 정의

### P1. 모바일 천지인 숙련자 (주 타깃)
30–60대. 스마트폰에서 천지인만 쓴다. PC에서는 독수리 타법으로 두벌식을 겨우 친다.
- **니즈**: PC에서도 아는 방식으로 치고 싶다.
- **성공 기준**: 설치 후 별도 학습 없이 첫날부터 입력 가능.

### P2. 접근성 사용자
운동 범위 제한, 저시력, 또는 스위치 입력 사용자.
- **니즈**: 타깃이 크고 적은 입력 인터페이스.
- **성공 기준**: 스캐닝 입력으로 12키 순회 가능, 스크린리더가 각 키의 현재 순환 단계를 읽어줌.

### P3. 키오스크/임베디드 개발자
좁은 화면에 한글 입력이 필요한 산업용 단말 개발자.
- **니즈**: 라이선스 명확하고 이식 쉬운 엔진.
- **성공 기준**: 코어를 단일 파일로 임베드 가능.
