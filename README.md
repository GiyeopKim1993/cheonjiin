## 실제 아티팩트 (로컬 실빌드 완료)

문서상 "구현 완료"가 아니라 **실제로 만들어지는지** 확인했다.

| 아티팩트 | 크기 | 검증 |
|---|---|---|
| `ime/android/build-apk/cuime-debug.apk` | 276 KB | 서명 유효 · IME 서비스 등록 확인 · `com.cuime` |
| Windows `cuime.dll` | 2.0 MB | PE32+ x86-64 · **COM 진입점 4종** (regsvr32 가능) |

```bash
cd ime/android && ./build-apk.sh      # Gradle 없이 aapt2/d8/apksigner 직접
cd ime/native  && ./build-dll.sh      # zig 크로스 컴파일 (MSVC 불필요)
python3 tools/check_pe_exports.py cuime.dll
```

이 과정에서 잡은 것: DLL이 **링크는 성공하는데 COM 진입점을 하나도 내보내지 않는**
상태였다(`STDAPI`만으로는 부족, `__declspec(dllexport)` 필요). 그대로 배포했다면
`regsvr32`가 실패했을 것이다. 또 TSF의 COM 계층이 실제로는 **주석 블록의 의사코드**
였음이 드러나 실제 구현(`tsf_com.inc`, 편집 세션·클래스 팩토리·등록)으로 대체했다.

## 물리 키보드 펌웨어

16키 하드웨어 키보드용 펌웨어. **하드웨어 비종속** 4계층 구조라 새 보드
이식 시 HAL 파일 하나만 쓰면 된다. 자세한 내용은 `firmware/README.md`.

```bash
cd firmware && ./build.sh    # 시뮬레이터 + 포트 정합성 + 전수 대조
```

```
port/   보드별 진입점 + HAL 구현 (esp32 / stm32 / rp2040 / sim)  ← 이식은 여기만
hal/    cuime_hal.h — 인터페이스 계약 5종
app/    정책 · 타이머 · 레이아웃 · 한자 후보 (하드웨어 무관)
core/   조합 엔진 (순수 상태기계, 시간을 모름)
```

| 보드 | 전송 | 상태 |
|---|---|---|
| ESP32 / S3 / C3 | BLE HID (ESP-IDF) | HAL 완성 · 실기기 미검증 |
| STM32 F1/F4/L4 | USB HID (CubeMX) | HAL 완성 · 실기기 미검증 |
| RP2040 / Pico | USB HID (TinyUSB) | HAL 완성 · 실기기 미검증 |
| POSIX 시뮬레이터 | 버퍼 | ✅ 통합 21항목 통과 |

**펌웨어 코어도 참조 구현과 전수 일치**한다 — 멀티탭 11,172자 / 롱프레스
11,172자 모두 불일치 0. 데스크톱 IME 와 한 글자도 다르게 동작하지 않는다.
`core/cuime_tables.h` 는 참조 구현에서 **자동 생성**하며(수기 이식 금지),
CI가 커밋본과의 일치를 강제한다.

HID 키보드는 유니코드를 못 보내므로, 조합된 음절을 **두벌식 자판 위치**로
분해해 전송하고 호스트 IME 가 합치게 한다(`가` → `r` `k`). 드라이버 설치가
필요 없는 일반 블루투스/USB 키보드로 인식된다.

전체 코드 크기는 **약 7.3 KB**(테이블 7 KB 포함, Cortex-M0+ `-Os` 기준).

## 단어 사전 정밀도

### 동음이의어 — 후보를 하나로 줄이지 않는다

초기 사전은 **29,361개 전부 후보가 1개**였다. 수집기가 여러 후보를 모으고도
`best` 하나만 저장한 탓에 `가정`을 치면 家庭 없이 假定만 나왔고, `사기`는
詐欺 없이 史記만 나왔다. 한국어에서 동음이의어는 흔하므로 이건 심각한 결함이다.

이제 유효 후보를 **전부** 보존하고 실사용 빈도 순으로 정렬한다.

| | 개선 전 | 개선 후 |
|---|---|---|
| 다중 후보 표제어 | 0개 | **3,013개 (10.3%)** |
| 총 후보 수 | 29,361 | **33,666** |
| 정답 세트 1순위 정확도 | 43/48 | **45/48** |

```
가정 -> 家庭 假定
사기 -> 詐欺 史記 士氣 射技
수도 -> 首都 水道 水島 修道 遂道
```

**정렬 가중치는 눈대중으로 정하지 않았다.** 사람이 고른 1순위 정답 50개
(`spec/word-rank-truth.tsv`)에 대해 격자탐색 + 5-fold 교차검증을 돌렸다:

```bash
python3 tools/tune_word_rank.py          # 재현/재조정
```

- 신호 3종: 어원 섹션 위키링크 수 · 문서 내 등장 횟수 · 구성 한자 상용도
- 각 신호를 0~1 로 정규화해 가중합 **(1, 2, 1)**
- 격자탐색 최적 **93.9%**, 5-fold 교차검증 평균 **89.8%** → 과적합 아님
- 5개 fold 중 3개에서 같은 파라미터가 선택돼 안정적

> 파라미터를 손으로 맞추다 `전화`가 電話→電火로 퇴행한 적이 있다. 그래서
> 정답 세트와 교차검증을 도입했다.

한국 한자음(Unihan `kHangul`)과 일치해야 한다.* 두음법칙(랑→낭, 려→여 등)은

## iOS 키보드 확장

> **v1.2 유예 해제.** 기존 스펙은 "`UITextDocumentProxy`에 marked text API가 없다"는
> 전제로 iOS를 미뤘으나, **이 전제가 사실이 아니었다.**
> `setMarkedText(_:selectedRange:)`는 [iOS 13.0+ **Required** 멤버](https://developer.apple.com/documentation/uikit/uitextdocumentproxy)다.
> 근거가 됐던 자료는 2014년 iOS 8 시절 답변이었다.

따라서 iOS도 **다른 플랫폼과 동일한 정식 preedit(밑줄 조합)** 을 쓴다.
delete-and-reinsert는 iOS 12 이하 폴백으로만 남겼고, 두 경로가 11,172자 전수에서
**동일한 최종 텍스트**를 냄을 검증했다.

```bash
cd ime/ios && ./run-tests.sh
```

## 핵심 설계 결정

1. **코어는 시간을 모른다** — 멀티탭 타임아웃을 셸이 소유하고 가상 키로 주입한다. 덕분에 테스트 벡터가 플랫폼 간 완전히 결정적이다.
2. **스냅샷 기반 멀티탭** — 멀티탭 직전 상태를 저장해 되감는다. 덮어쓰기 방식으로는 `삶`·`많` 같은 겹받침이 불가능하다.
3. **`▶`가 확정 키를 겸한다 (16키)** — 음절 내부 멀티탭 충돌이 0건이므로, 방향키가 타임아웃을 100% 대체한다. 결과적으로 **타임아웃을 완전히 끌 수 있다** — 접근성상 중요한 이득.
4. **롱프레스 쌍자음으로 기능키 소멸을 상쇄 (16키)** — 획추가/쌍자음 키를 잃었지만, 롱프레스 도입 시 6.357타로 12키(6.691타)보다 **5% 빠르다**.
5. **`漢` 키는 뗄 때 판정한다** — 누르는 순간에는 단독 탭인지 코드 시작인지 알 수 없다. `hj_consumed` 플래그가 없으면 레이아웃 전환 후 손을 뗄 때 기호 팔레트가 같이 뜬다.
6. **영어는 ITU-T E.161 표준을 따른다** — 키 2개가 남아 `PQRS`/`WXYZ`를 쪼개면 4% 빨라지지만(2.155→2.069탭), 전 세계 키 각인과의 일치가 우선이다.
7. **롱프레스 = 순환열 마지막 항목** — 단일 규칙이 한글 쌍자음·ㄹ·ㅁ과 영어 S·Z를 모두 커버한다. 규칙을 단순화했더니 타수도 7.3% 줄었다(6.357→5.894).
8. **천지인이 두벌식보다 느리다는 사실을 인정한다** — 1.418배. 속도가 아닌 연속성·접근성으로 포지셔닝한다.
